Multica

组织成可管理的团队

ARCHITECTURE

01 / 它在系统中的位置

Multica 是编码 Agent 的任务控制平台，而不是新模型或统一推理引擎。它把现有 CLI 变成可派工、追踪、续接和交付的团队成员。

交互层

Next.js Web、Electron 桌面、Expo / React Native 移动端。人类与 Agent 共同围绕工作项协作。

控制层

Go、Chi、sqlc、PostgreSQL 与 WebSocket。管理记录、触发、领取、额度和生命周期。

执行层

Daemon 调用已安装并登录的编码 CLI。模型推理与多数代码工具循环仍由底层 Provider 实现。

EXECUTION

02 / 从一条 Issue 到一次执行

① 触发

分配活动 Issue、评论、Chat 或 wakeup 可产生持久队列任务。仅把任务放在 backlog 通常不意味着立即启动。

② 领取

Daemon 先占本机执行槽位，再领取工作。服务端同时核对 Agent 与 Runtime 容量，数据库使用 FOR UPDATE SKIP LOCKED 避免重复领取。

③ 准备

建立或复用工作目录，装入 Agent 身份、项目资料、skills、MCP 与任务级凭据；尝试找到同范围内可恢复的 Provider Session。

④ 执行

调用 CLI，流式解析消息、工具、usage 和错误，回传到控制平面。运行中补充输入能力依 Provider 而异。

⑤ 记录与后继

保存结果和 Session 指针；评论或业务状态变更可触发下一步。基础设施失败有分类重试，但不意味着所有业务失败都会被修好。

Run 完成 ≠ Issue 完成。Leader 派单后可以正常结束本轮，但父 Issue 仍未完成。一次执行退出只是运行生命周期终点，不是系统自动认定验收通过。

并发不是一个全局单队列：同一 Agent + Issue 串行，聊天按 Agent + Chat Session 串行；不同 Agent 可以同时处理同一 Issue。并行上限还受到 Daemon 和 Runtime 容量制约。

COLLABORATION

03 / Agent 如何派工、汇报与接力

协作的主通道是 Issue 评论事件。Agent 使用结构化 mention 链接指向其他 Agent；平台解析接收者，为对方创建独立执行。普通文本的“@名字”并不等价。

Squad Leader

读取任务、成员 roster、技能和验收要求，选择成员，通过评论委派，记录 evaluation，随后结束本轮。后续成员结果、提问或新的触发再让它继续判断。

Worker

通过自己的 CLI 和上下文执行，把结果写回 Issue。Agent 评论不是无条件广播唤醒所有人；显式 mention、Squad 回流和不同来源的隐式路由有各自规则。

一次派工选一种路径。若同一工作既建立并分配子 Issue，又在父 Issue @同一个成员，可能启动两次执行。平台不会自动推断两者其实是一件事。

WORKFLOW

04 / 子任务与工作流：有结构，但不是全自动计划器

Multica 支持父子 Issue、阶段分组及开发 → 审查 → QA 工作流。状态变更能够触发下一位接手，但不能把“Run 成功退出”当成业务步骤自动完成。

内置指南倾向于一个 Issue、一个 Agent、一个 PR，只拆真正可以独立合并和验证的工作。阶段关闭后，服务端可唤醒父任务负责人；是否将下一阶段从 backlog 提升到 todo，仍要由负责人检查依赖后决定。

成员之间持续相互 mention 的终止条件，也需要任务协议和指令约束。排队、去重和合并能减少重复运行，不负责判断讨论是否已经足够。

MEMORY

05 / Session 与记忆：三种状态，不能混为一谈

业务记录

服务端持久保存 Issue、评论和附件。每个 Agent 可获取任务相关资料，但不自动拥有其他 Agent 的私有推理会话。

会话续接

查找同 Agent、同 Issue 的历史 Session，Runtime 相同才尝试恢复。Chat 有自己的会话范围，丢失、污染或退役的 Session 可能被跳过。

长期经验

Skills 与 Agent 指令可复用，但不是从经验自动学习出来的统一记忆。Provider 原生 memory 的范围与开关也不同。

Codex：优先避免串扰

任务 Session store 按 Agent 与 Issue / Chat 范围保存。Codex 原生长期 memory 默认关闭，目的是避免宿主或其他任务的记忆跨工作区混入；可以显式启用，但不能因此称为全团队共享记忆。

Hermes：跨任务记忆，但存在写入竞争

Hermes 的 agent/profile 级 memory 可以跨 Issue 保留，不同 Agent 不共享。同一个 Agent 并发更新仍可能后写覆盖先写；部分无 skill 路径也有宿主 home 使用边界，不能把所有路径一概说成严格隔离。

未见一套统一跨 Provider 的向量记忆或自动摘要记忆层。换模型或机器后，工作记录可以帮助重建背景，但不能恢复 Agent 没写下来的全部内部状态。

BOUNDARIES

07 / 三个最容易误解的边界

① 平台多 Agent ≠ Codex 原生子 Agent

Multica 的多个成员是多个可管理的独立 Run。当前 Codex 原生 multi-agent 默认被禁用：源码解释，平台只追踪父 thread，父 turn 完成时子 Agent 可能尚未结束，因而丢失输出。显式 opt-in 不代表生命周期问题已解决。

② 工作目录 ≠ 安全沙箱

默认执行拥有 Daemon 所属操作系统用户的文件、凭据和网络权限。Claude 使用 bypassPermissions，Codex 默认 danger-full-access；Windows 的显式原生 sandbox 是特定例外。目录、task token 和 CODEX_HOME 减少串扰，不足以隔离敌意代码。

建议：在专用用户、容器或 VM 中运行；缩小凭据与网络权限；用 Git 分支保护落实合并约束。人工 Review 流程本身不是绝对安全门。

③ 本地执行 ≠ 数据绝不离开机器

代码执行在本机，不代表模型请求不会发往远程服务；运行日志也可能回传控制平面。隐私边界取决于 Provider、模型端点、日志和凭据配置。

COMPARISON

08 / 与 TogoSpace 放在一起看

维度TogoSpace（此前固定版本）Multica（本次固定版本）
协作中心Room、发言轮转与 Agent 连续历史Issue、评论事件、Run 与工作流
任务接力创建任务不直接唤醒；显式发消息结构化 mention、状态变更、Squad 回流触发
会话范围每 Agent 跨房间连续历史按 Agent + Issue / Chat + Runtime 尝试续接
上下文控制项目自己做摘要压缩，保留工具调用尾部主要依赖 Provider Session 和按需读取任务记录
并发方式每 Agent 串行消费Agent / Runtime 容量配额，同 Agent + Issue 串行
工程重心长期成员在多个房间连续协作管理已有编码 CLI 的执行、交付与恢复

TogoSpace 更像有规则的团队协作房间；Multica 更像 Agent 的项目管理与执行控制台。这是设计重心的差异，不能从中直接推出智能、效率或任务成功率谁更高。

ASSESSMENT

09 / 值得借鉴什么，实际部署前还要验证什么

值得借鉴

  • Issue 作为可重读、可审计的协作记录。
  • Run 生命周期与业务完成状态分开。
  • 先占容量再领取、数据库并发控制和失败恢复。
  • 稳定提示前缀与动态输入分离。
  • 以任务范围约束 Session 和环境，减少上下文串扰。

仍需实测

  • 真实 CLI 的恢复、流式格式和工具行为。
  • 多 Agent 并发改同一仓库时的冲突。
  • 评论往返的循环终止与任务验收质量。
  • 异常退出、失联、重复触发是否产生副作用。
  • 运行日志、宿主凭据和 Provider 数据边界。

仓库包含并发领取、成员评论唤醒 Leader、Chat Session fallback 等回归测试，说明维护者在处理真实工程问题。本次只阅读代码与测试源码，没有运行应用、测试或真实 CLI。测试文件存在不等于本次测试通过。
