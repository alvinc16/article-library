01 / 先建立正确的系统模型

TogoSpace 将组织结构、聊天房间、任务单、模型执行与持久化历史组合成一个 Agent 团队运行时。其核心不是预先编排好的一张 DAG，而是消息触发调度、模型通过工具协作、任务单维护跨轮次状态。

Room消息与发言调度

保存成员、消息序号、已读位置与当前发言者。不是独立模型上下文。

Agent长期运行单元

持有任务消费者、执行器与历史。跨房间、跨任务连续工作。

Task可追踪的协作承诺

记录指派、状态、依赖与事件，不等同于立即启动 Agent 的调度记录。

并发边界：不同 Agent 可以并发，但同一个 Agent 的任务串行处理。因此“开多个房间”不是“让同一 Agent 同时拥有多个隔离推理线程”。

02 / Agent 到底如何相互交互

① 发消息必须调用工具

send_chat_msg 向已有房间发送消息；代码检查房间所属团队与发送者成员关系。start_chat 查找或创建两个 Agent 之间的私聊。模型的普通文本输出并不等于消息已发送。

② 消息进入房间存储

Room 保存消息和递增序号；每个 Agent 有自己的已读游标。对方不是读取你的完整模型上下文，而是收到被投递到共享房间的内容。

③ 发言状态变化产生调度

房间状态变化经进程内 asyncio 事件传递给调度器，后者写入数据库调度任务并启动目标消费者。ROOM_MESSAGE 的优先级高于 TODO_TASK，同类按记录 ID 排序。

④ 未读消息变成模型输入

轮到某个 Agent 时，取未读且非本人发送的消息，组装为含房间、发送者、时间与内容的 YAML，再写入该 Agent 历史，作为本轮 USER 输入。

⑤ 工具循环结束后交棒

Agent 用 finish_action 结束行动。群聊会在达到最大轮数或所有 AI 都跳过时停止；私聊没有同样的最大轮数限制，所有 AI 跳过后停止。

发言位不是由另一个 LLM 临时挑选。RoomScheduler 按成员列表循环推进，自动跳过 Operator，也避免上一位发言者紧接着再次发言。业务分工动态生成，但单房间的轮转仍由确定性状态机约束。

运行中插入不是任意抢占。补充消息在不破坏工具调用 / 结果配对的安全边界注入。主循环重点检查 Operator 控制私聊；普通私聊消息可能等到当前轮完成后再处理。

实际含义：Agent 之间共享的是明确发送的消息、任务事件与共享目录文件，不是自动共享彼此的全部思考历史。团队结构和负责人规则主要影响模型行为与可用信息；消息存储和调度状态机决定具体执行顺序。

03 / 任务单与执行队列：最容易混淆的两层

协作任务单

给人和 Agent 看的工作对象：标题、说明、执行人、状态、依赖、验收与事件时间线。用于跨轮次保持工作目标。

调度任务记录

给消费者看的待执行记录：某 Agent 应处理房间消息，或继续某项 TODO。消费器决定何时执行。

create_task 只创建任务，不自动唤醒执行人。要让对方及时工作，还需要通过消息工具通知。消费者在一轮成功完成后扫描自己的活跃协作任务；依赖完成后从 PENDING 自动转成 TODO，也不等于立刻唤醒。

状态与权限是代码约束

业务状态包括 TODO、PENDING、IN_PROGRESS、REVIEWING、ON_HOLD、DONE、CANCELLED。可指派给自己或直接 / 间接下属；有验收人时，执行人必须先进入 REVIEWING，不能直接 DONE。验收人通过或打回；取消权属于创建人或验收人。终态只能追加评论，不能重新变更状态。

状态和事件在同一事务中写入，再广播通知。事件列表可截断，单事件查询返回完整内容，形成“先看摘要、再查详情”的模式。

priority 字段不等于队列优先级。业务任务当前按 ID 选择最早活跃任务，没有按 HIGH / NORMAL / LOW 排序；房间消息又优先于 TODO_TASK，因此高频聊天可能推后任务执行。

任务创建与权限 ↗实际任务选择 ↗

设计上的优点：聊天与工作状态分离，不需要从大段对话反推每项承诺。代价：唤醒依赖消息与后续扫描，不能将它描述为“任务一建好就全自动运行”的通用工作流引擎。

create_task ↗任务扫描 ↗依赖推进 ↗

04 / 每个 Session 如何管理

必须区分四个概念：Room 是消息场景；turn 是一次行动；Agent history 是跨轮次上下文；session ID 是依据当前历史边界生成的上游请求标识。

事件Agent 历史Session ID
收到新消息 / 切换房间追加本轮输入，保留已有上下文通常不变
处理协作任务追加任务通知；并非清空成“只有任务说明”通常不变
压缩上下文新摘要成为当前窗口首行，保留必要尾部切换
进程重启Native / TSP 路径从数据库恢复当前窗口同一边界得到同一确定性 ID

ID 由 agent_id 与当前历史首行 ID 确定性生成 UUIDv5。压缩摘要创建新的首行，所以成为 session 的自然分界。

不要把它理解为远端会话存储。Native / TSP 请求仍由应用发送 system prompt 和当前历史，ID 进入 X-Session-Id 做上游关联。仅传一个 ID 并不能替代上下文。

落库与异常恢复

  • agent_histories 保存 agent_id、seq、角色、内容、工具调用关联、状态、标签和 usage；agent_id + seq 有唯一约束。
  • 运行前写 INIT 占位，结束后完成记录，BEGIN / FINISH 标签标识 turn 边界。
  • 重启恢复最新 compact 之后的历史，以及房间消息、阅读位置与发言状态。
  • 遗留 RUNNING 调度任务改为 FAILED。重新启动消费者后才能继续处理，不能宣称任何中断都会自动无缝续跑。
  • 工具已产生外部副作用、结果尚未落库时仍存在崩溃窗口。这不是通用 exactly-once 工具事务保证。

05 / 记忆系统：历史、摘要、任务与文件

对话记忆

数据库全量历史 + 当前内存窗口 + LLM 压缩摘要。

协作状态

房间消息、已读位置、任务主表与任务事件。

工作文件

Agent 私有工作目录与团队共享目录，按工具与工作流读写。

在核查的运行核心、工具及路径树中，未发现独立向量库、embedding 检索、用户画像记忆层或自动记忆整合机制。有持久文件，不等于内置了会自动归纳和检索的文件记忆系统。

上下文压缩的实际过程

默认配置使用 131072 上下文、16384 输出预留及 0.85 触发比率，但均可配置，部分模型还有窗口兜底。摘要以 USER 消息写入，标签为 COMPACT_SUMMARY。被压缩的数据库旧消息不删除，只是当前运行窗口不再全部携带。

配置字段与运行行为的一个偏差

默认触发点按“上下文窗口减输出预留，再乘触发比率”计算，约 97,484 tokens。估算优先使用 token counter，失败回退字符数 / 4，不能当成精确计费。

配置虽有 compact_summary_max_tokens=6144，当前 Runner 却以窗口的 10% 设置摘要目标。该目标进入 Prompt，并不是该次 API 调用的独立输出上限；API 上限仍由输出预留配置决定。

实际摘要预算 ↗配置定义 ↗

摘要是模型生成的有损记忆，可能遗漏约束。旧记录可追溯不等于模型每轮自动查询旧记录；没有证据就不能把数据库存档称为“自动召回”。

团队共享目录的作用

大文件、代码和交付物可通过文件协作，减少把所有内容塞入聊天。私有目录与共享目录的约定由 Prompt 告知 Agent；是否形成良好的笔记习惯仍依赖角色指令、工具行为和人的工作流。

07 / 三种 Driver 并不完全等价

TSP 是工具协议，不是 Agent 间通信协议。它通过子进程 / TSPClient 提供文件与命令执行工具，Agent 协作依然走 Room / Task。TSP 执行环境切换状态在内存，重启回到宿主，不能假定曾进入容器便永久留在容器。

默认配置是 TSP。Native 与 TSP 使用由宿主程序管理的循环；Claude SDK 路线把更多执行状态留给 SDK 客户端。

维度Native / TSPClaude SDK
上下文发送应用持有并发送当前 system + history长期 ClaudeSDKClient；query 发送增量 turn prompt
重启后的恢复有数据库 history 恢复路径startup 未见 resume 参数或数据库历史 replay
TODO_TASK宿主管理任务轮次run_task_turn 缺少 room_id 即返回，能力不能视为对等
压缩与会话宿主管理摘要与 session 边界不能把同一恢复语义直接套用到 SDK
权限模式需逐工具检查实现和环境权限配置中使用 bypassPermissions，应额外关注执行隔离

08 / 设计取舍与需要验证的地方

值得借鉴

  • 把房间消息、协作任务与执行调度分层，状态更明确。
  • 每 Agent 串行队列降低同一历史被并发修改的复杂度。
  • 完整历史落库，摘要窗口与存档分离，可审计可恢复。
  • 用角色模板和技能摘要组合行为，不把一切硬编码成单一大 Prompt。
  • 明确通过工具发送和结束，让模型输出与外部行动有可观察边界。

代价与风险

  • 跨房间复用历史可能让无关上下文相互影响；不是会话隔离。
  • 任务状态推进不自动唤醒，依赖模型正确通知及后续扫描。
  • 摘要有损；数据库存档不能自动弥补当前上下文遗漏。
  • 外部工具副作用没有通用 exactly-once 保证。
  • 不同 driver 能力不对称，配置切换不是纯性能选择。

Prompt 不是审批系统：负责人先询问人类是行为指导，不是独立后端审批。默认工具授权 None 包含 Basic、Read、Write、Execute，Basic 强制保留，最高负责人还自动添加 Admin。需要严格隔离时，不能只靠角色措辞或 Room 成员检查。

工具权限策略 ↗

如果继续做工程验证，我会优先测这些

  1. 跨房间隔离：同一 Agent 交替处理两个主题，看约束和事实是否串扰。
  2. 建单不通知：仅创建任务、随后补发消息，记录执行触发差异。
  3. 压缩中断：工具调用尚未闭合时压缩，验证调用 / 结果成对和摘要边界。
  4. 重启恢复：在模型返回前、工具执行后、历史写入后分别中断，检查是否重复副作用。
  5. 多驱动一致性：分别验证 TODO_TASK、恢复、控制私聊中断和结束语义。
  6. 提示注入：外部内容进入 room USER 消息或共享文件时，检查它能否越过组织规则和工具边界。

以上是建议测试，不代表已执行或已经证实存在漏洞。本报告仅做静态源码核查。

09 / 建议的源码阅读顺序

  1. 先看 Agent → Consumer → TurnRunner，建立执行对象与生命周期。
  2. 再看 RoomScheduler → MessageBus → SchedulerService，追踪一条消息如何变成执行。
  3. 接着看 PromptBuilder + prompts.py + role_templates，确认实际模型输入。
  4. 随后看 AgentHistoryStore + compact + sessionUtil，理解记忆与 session 边界。
  5. 最后对比各 Driver，确认哪些结论只适用于默认 TSP 路径。

核心心智模型：房间负责沟通，任务负责承诺，队列负责执行，Agent history 负责连续性，压缩摘要负责控制上下文预算。
