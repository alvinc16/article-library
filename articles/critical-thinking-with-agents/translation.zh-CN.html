当 Agent 替你工作时，
如何保持批判性思维

Critical thinking when agents do the work

译文说明：本文按你提供的英文全文翻译，保留原文结构与第一人称叙述；文中的“我”指原作者。Agent 保留英文称谓。为避免歧义，deferral 译作“判断让渡”，指把模型输出直接当作后续判断的前提，而非“拖延”。重点高亮为阅读辅助。

以前，人们教我们批判性思维时，强调的是以谦逊的好奇心和适度的怀疑去接触新信息：听取不同观点，再形成自己的看法。这些仍然成立。可如今，我越来越觉得，既然这么多工作都交给了 Agent，日常工作里已经没有什么会迫使我进行批判性思考了。对于那些已经全面拥抱 Agent 工作流的工程师和产品人员——同时运行多个会话，并期待模型继续进步的人——我想先说明：我非常喜欢这些工具。我写这篇文章，并不是为了倡导减少使用 Agent 工作流。

我的目标，是帮助你在一个什么都很容易交给 Agent 的世界里，保持批判性思维。

过去，我们的大部分认知加工与审美判断，都发生在问题与答案之间的空隙里。如今，这段空隙只剩几秒钟。Agent 工作流用得越多，这件事就越难，尽管困难的方式可能不是大家原先预想的：随着模型进步，明显错误的比例越来越低。许多，甚至大多数输出，都会写得很好，而且基本正确，但它们不会让你觉得有必要再看一眼。

即使你同时运行着许多 Agent，查看输出的也仍然只有你这一双眼睛。

你必须主动把批判性思维安排进日常工作，否则默认情况下，没有什么会替你做到这一点。

之所以难以自行纠正这种倾向，一部分原因在于 Agent 工作流用起来很舒服。在忙碌的一天里，迅速得到令人满意、而且往往正确的答案，确实让人轻松；但也正因为如此，我们很容易放松警惕。

01｜认知卸载、判断让渡与认知投降

和别人讨论这个问题时，我会把它描述成一条连续谱。

最上端是“认知卸载”：把任务交给 AI，但仍然对结果负责。我每天都这样做，你也应该这样做。中间是“判断让渡”（deferral）：工具的输出成为你的新输入，而这个结果已不再被当作一个有待验证的假设。最下端则是“认知投降”：AI 的输出悄悄成了你自己的想法，你不再觉得有必要检查它。

“认知投降”这个术语由沃顿商学院的 Steven Shaw 和 Gideon Nave 提出。它恰好描述了我观察到的现象：随着信任增加，或者人变得更懒，人们沿着这条连续谱逐渐下滑。这个转变很少被注意到，因为每一步都很渐进，看起来也都合理。上一个答案你认真读了，于是下一个就略读；再下一个，你只扫了一眼框架。然后，有人问起其中某一行，你却解释不清，甚至有 Agent 帮忙也说不明白。

这就是认知投降，也是认知债务累积的方式。通常，直到你试图运用自己对系统的心智模型，却发现这个模型根本不存在时，问题才会暴露。Margaret-Anne Storey 写过，这种现象在团队里表现为：大家对系统运行原理的共同理解逐渐被侵蚀。我也写过它在代码中的对应物——“理解债务”（comprehension debt），这个术语由 Jeremy Twei 提出。当下，这类债务完全不可见：代码库看起来整洁无瑕，测试全部通过。直到你必须修改系统，才发现已经没人理解它了。如果你只是读了战略文档或规格说明的目录就批准了它，情况也一样。

说清楚一点，我并不是在要求一件不可能的事。要在脑中保有一个大型现代代码库的完整心智模型，是不可能的。Claude Code 团队曾公开表示，他们会按需重建理解：需要理解某一部分时，就请 Claude 解释那一块，而不是把整个模型都装在脑子里。正如我此前写过的，这类债务比大多数工程师想象的更容易补回来。只要能在需要时重新理解局部，就不必始终维持完整模型。你只需要知道自己缺少哪部分理解。

风险很低时，完全委托也无妨。但如果连借助 Agent，你都无法解释一个问题的答案，那你已经让出了对结果的掌控。

这也并非总是问题。就在不久前，我录制一门课程，需要从三家评分相近的酒店中选一家作为录制地点。我没时间逐条查看所有评论，于是把决定交给了 AI。结果很好，下次我还会这样做。不过，在决定如何投资家里的钱、如何给孩子提供职业建议，或者在工作中决定应该做什么产品、哪些变动会影响哪些用户、发布是否安全时，我不会这样做。判断错误的代价很低时，可以交出去；如果后果要由别人承担，就保留自己的推理和判断。

02｜我会问自己的问题

以前，当我不确定自己怎么想时，通常会回到一些基本问题：我怎么知道自己正在解决正确的问题？我怎么知道解决方式是对的？有没有证据支持我的结论？我怎么知道工作已经完成？大多数时候，这无非就是谁、什么、哪里、为什么、何时以及如何。写出来似乎幼稚得可笑，但它会迫使你从一些原本可能忽略的维度去思考。如今，我们太容易跳过这些，直接问 Agent 觉得我们该怎么做。下面是我现在会问自己的新版问题。

在提问之前，我有没有先形成一个假设？ 在让 Agent 处理任何不那么简单的任务之前，我都会先写下，哪怕只是在脑海中想一下，我认为答案可能是什么。猜得不好也没关系；面对新信息，你随时可以改变看法。可是，一旦读过一份写得很好的回答，就很难再想象其他可能性。如果你完全没有方向，可以尝试 Thariq Shihipar 所说的“盲点检查”：把你已经知道的告诉模型，让它找出那些你连自己不知道都没意识到的东西。

我是在让它帮助我思考，还是在让它替我思考？ 两种都可以，只要你清楚自己在做哪一种。

什么情况成立时，这个结论就会是错的？ 然后去查证。模型对自身信心的评估，远不如你真正能够执行的一次检验有价值，所以给它一个实际检验。

我有没有从不同角度听过反对意见？ 当我对某个比较开放的问题持有很强的立场时，我会让不止一个模型为相反观点辩护，然后审阅输出，再形成自己的看法。这更费时间，但最后我会对这个主题了解得多得多。

面对将来必须维护它的人，我敢不敢为这个结果打包票？ 这既适用于代码，也适用于你交付的任何东西。我认为，这就是能否对结果作出交代的标准。

哪些技能，我已经不再练习了？ 也许是某些常规调试。我可以接受放下其中一些，但我希望这是有意识的选择。

03｜把验证变成习惯

最近我写了很多关于验证的内容，因为我相信，瓶颈已经从编写代码转向了确定自己确实做对了。当你给 Agent 提供验证自身工作的手段，无论是端到端测试、属性测试，还是实际操作应用，它就能在你还没看任何东西之前，完成修改、运行验证、阅读输出，再尝试一次。Boris Cherny 把这称为“给 Claude 一种验证自己工作的方式”，我认为这是取得优秀结果最关键的组成部分之一。你不再逐行阅读所有代码，而是构建这些验证循环，并审阅证据。

你也可能在验证上选择投降。“有没有证据支持我的结论？”会变成“检查有没有变绿？”Agent 让编写测试变得非常便宜，于是你会看到大量绿灯，但一个通过的测试，也可能根本抓不住已经损坏的功能。如果测试和功能实现犯了同一种错误，测试照样会通过。而且，一个绿色勾号只说明某一项性质成立。我们太容易想象它覆盖了所有事情。

检查变绿时，问问它证明了什么。然后再问，它没有证明什么。

提前定义什么叫“已验证”，因为事后你会为任何结果找理由。

Agent 工作的终点应该是有形的东西：一个通过的测试、一张截图、一份日志或一段执行追踪。这样，完成标准就基于事实，而不会因为“看起来好像做完了”之类的感觉，变成可以任意解释、甚至放弃判断的东西。收到 Agent 的完成通知时，先别看摘要，先查看它实际执行的命令片段以及输出。

Claude Code 也能通过处于全新上下文中的子 Agent，对自己的工作进行自我批评，做一次合理性检查。值得把这一步放进循环，让它每次都运行，而不是等你想起来才做。我最后仍然会问一句：“我有没有漏掉什么？”这听起来有点傻，但很多时候，我用前沿模型完成一项复杂功能，看过、审过之后，再问这句话，它就会补出两三件事。所以我总会问。

当然，你不必每次都做到这种程度；知道什么时候该深挖，本身就是一种技能。在我们关于 Claude Code 团队如何做代码审查的文章里，我最喜欢的一条经验是：“如果你说不清这些检查会漏掉什么，就要求一次真正的审查，而不是快速批准。”

这也适用于代码之外的工作。如果 Agent 为你综合了五十通客户访谈，或者做了一份竞品分析，就抽查几份原始材料，确认摘要准确。对于建议所依赖的数字，也要检查它是否计算正确。

Agent 已经让建立验证机制变得便宜。对你而言，难的是知道什么才算好的验证。

04｜真正留意生成出来的内容

假设 Agent 给你一个六百行的 PR。你大致看了看结构，没有逐行阅读。变量名看起来合理，测试也都通过，于是你批准了它。但中间某处，也许悄悄改变了事务边界上的执行顺序，或者把一个你从未想到的边界情况的默认值反转了。你大概也算审查过，只不过你检查的，仅仅是你本来就知道要找的东西。

编写代码和审查代码是两种不同的技能，而审查到了某个程度，就会变成盖章走过场。所以，请像审查非 AI 编写的代码一样阅读差异，然后越过差异本身，看看 Agent 作了哪些决定。一个漫长的会话里，它会替你做许多小决定：默认值是什么，哪些事情不在范围内，两项要求冲突时，它重新解释了哪一项。

在一份声称“一切顺利”的摘要里，你看不到这些，因此，要让它列出自己做过的决定和假设。然后考考自己：随机挑几行，问问这一行是怎么回事，那一行又如何。对于文档，可以把它关掉，再试着凭记忆写出主要论点。有些人在长会话中有个我很喜欢的习惯：让 Claude 写一份变更报告，并在末尾附上一份测验，规则是“只有测验全部答对，我才会合并”。

你需要充分理解自己交付的东西，理解到能够为它作出解释、为它辩护。因为总有一天，可能有人会问。

Agent 也可以帮你保护注意力。例如，我有一个开源项目，会收到很多拉取请求。我会用 Agent 帮我判断有哪些新请求、哪些不符合我们的准则，以及哪里可能需要我的注意。我很少让 Agent 自行作最终判断，但它们可以帮我把关注范围缩小，让我真正去思考这些变更是否在用正确的方式解决正确的问题。

还有一个问题是产出量，你必须诚实面对它。我把这叫作“编排税”：Agent 生成的东西，与那些你愿意署上自己名字的东西之间的差距。如果已完成的工作堆积得比你处理得还快，那么在解决这个问题之前，多开一个会话毫无帮助：要么加强检查，让需要你亲自处理的内容减少；要么放慢速度。

当你的产出多到你无法为之负责时，你就不再是在审查，而是在寄希望于它们没问题。

05｜高质量输入，才有高质量输出

人的心智模型仍然参与其中，只是从中间移到了开头和结尾。你的精力投入在任务前端的描述与上下文，以及后端的输出审查上。这就是优质输入对输出质量如此重要的原因，我也因此把写好提示词视为一种批判性思维技能。

过去，如果你提出一个不够具体的要求，往往会有人追问，让你意识到：“等等，其实我自己还没想明白。”Agent 通常不会在这里拦住你。它会填补你没说清楚的部分，然后交回一个看似完成的结果，尽管背后的想法依然模糊。我写过这种“意图债务”：在并非你亲自编写的产物中，可能存在隐含的目标、约束和理由。不同于其他债务，这一种没人能替你解决。意图必须来自你自己。

提示词反映了你对问题的理解。如果你表达不清楚，也许这个问题在你自己脑中就还不清楚。

请求帮助之前，先用自己的话写一份需求简述。说明受众、不在范围内的事项，以及完成的定义。如果第二轮修正之后仍然没达到目标，就别继续小修小补了，重新写提示词。

你也可以让 Agent 协助这个过程。我喜欢 Andy Clark 对“把事情委托给 AI 系统”和“与 AI 协作”的区分。后者是一种相互增强的良性循环：提示词让输出更精确，输出又帮助你改进下一次提示词，并进一步澄清你对问题的心智模型。如果事情还不清楚，就让 Agent 围绕它不理解的部分采访你。如果结束会话时，你自己的心智模型也变得更清晰，那就是成功的迹象。

也要小心输入内容。每个 Agent 都很容易只把前一个 Agent 的摘要放进自己的上下文，不久之后，第三个 Agent 就根本没读过原始文档。

你还需要有自己的输出标准。我在许多不同的创作媒介中尝试过 AI，但其中大多数成果从未拿出来展示，因为没有达到我的标准。现在，一切都能显得排版漂亮、语气自信，因此精致的表面已经不再是有用的质量信号。

AI 或许让生产变快了，但如果我不愿意把某份输出署上自己的名字，我就不会把它交出去。

当某个结果没有达到你的标准时，把原因记入共享配置、hook 或测试，避免同样的事情再次发生。品味就是这样逐步积累的；而且，记录为什么某个东西没能过关，本身就是很好的练习。

06｜“但模型会比我更擅长这些”

如果你像我身边很多人一样看好这个领域的未来，读到前面几节时，你可能已经在想：再过一两年，模型就能发现我能发现的问题了，那为什么还要费心保持这种技能？

在很多问题检测能力上，你可能是对的；我自己也一直主张把越来越多的检测工作交给 Agent。但我认为它仍然重要，原因在于：归根结底，总得有人对最终交付的东西负责。不管 AI 帮了多少忙，承担责任的仍然必须是人。

对于任何给定任务，到底应该信任 Agent 到什么程度，本身就是一种判断。保持判断准确的一部分，就是审查工作，因为模型会犯的错误一直在变。Anthropic 对自家工程师和研究人员的研究，把这个陷阱称为“监督悖论”：“监督 Claude 所需要的，恰恰是那些可能因过度使用 AI 而退化的编程技能。”

有些问题对我最为重要，而更好的模型也无法替我解决：你要构建什么？为什么值得做？它会影响谁？你愿意牺牲什么？这些问题都需要你来回答。Agent 可以帮助你逐一想清楚，我也希望它能帮忙，但最终，这些问题仍然属于你。

你可以把工作和大量审查交出去，但不能把责任交出去。

07｜日常实践

你不必严格执行这里的所有做法。挑选适合自己工作流的部分就好。

每周一次，不用 Agent 写一点代码，或者亲手做一件如果忘记怎么做、你会觉得很糟糕的实事。我把它称为“校准练习”，但并不是从道德层面提出的。每月一次，写下自己已经不再做哪些事，并决定其中哪些是你可以接受不再做的。我以前一篇博客中的问题，到今天仍然有效：如果 AI 不存在了，你会有多不知所措？

如果某件事超出了你的理解，就去学习。写作时，如果我遇到一个从没见过的短语，我可以搜索一句话的解释，然后把它写进文章。但我更愿意稍微研究一下，真正理解它，这样才知道它适合用在哪里。

认真检查机器的工作，本身就是实实在在的工作。假装这件事不算工作，正是团队最后不去做它的原因。它不是免费的，所以把它作为单独一项安排进日程，你才会真正完成它。

不再练习的技能会消退，而且可能比你想象得更快。对于那些你不愿放弃的技能，请继续使用它们。

08｜请带走这些提醒

有意识地行动。 Agent 可以考你、采访你、展示证据，但前提是你安排了这些步骤。所以，把它们安排进去。

诚实面对自己在连续谱上的位置。 如果有 Agent 帮助，你仍然解释不清答案，那你已经把判断交出去了。

先有一个假设。 提问之前先形成假设，哪怕它并不好。

一个绿色勾号只说明一件事。 它检查了什么？又没检查什么？

寻找证据。 在读摘要之前，先看它运行了什么，以及返回了什么。

阅读，是为了知道它做了哪些决定。 它替你决定了什么？

认真打磨提示词。 你的提问方式，体现了你对问题理解得有多深。

设定标准，并坚持它。 如果你不愿意署上自己的名字，就不要把它交出去。

通过亲自运用重要的技能，让自己继续参与其中。你可以试着做一件事：提问之前，写下你认为会发生什么；Agent 完成后，再写下一件它没有检查的事。告诉我，这是否改变了你阅读输出的方式。独立思考，提出更好的问题，并对结果负责。
